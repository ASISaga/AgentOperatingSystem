# DECLARATION.md — the purpose, and the Boardroom MVP is live

This is not a Task. It has no `state`, resolves to no `completed`. It is
the thing every Task in this exchange now serves, and it does not change
because a Task does.

## The purpose (locked, company-authored — `boardroom-spec 16`)

**The purpose of the Boardroom is the exponential, unstoppable,
ubiquitous, unconstrained, plural, generative expansion of the Founder's
reach — their purpose, judgment, and decisive capacity.**

Stated by the Leader, for ASI Saga, as the root every derived purpose in
this constellation ultimately answers to — `purpose_version: 1`, locked
this revision, refinable empirically later, not architecturally closed.
Not the Architect's derivation standing in for the company's own
statement (an earlier revision of this file carried exactly that,
explicitly marked as provisional); this is the real root.

Everything below — the moment, the shortest path, what a Task must serve
— was already true before this purpose was stated. It reads differently
now that it's named: not a mechanism that happens to enable good
deliberation, but the concrete, checkable shape of what "expansion of the
Founder's reach" requires to be real rather than rhetorical. Plural reach
means self-derived purpose per role, never a copy. Generative reach means
value-chain synergy, non-commensurable judgment that cannot be averaged
into something smaller than what it held. Unconstrained means the chair
authors rather than computes, so no ceiling is quietly imposed by the
mechanism itself.

## What's declared, as already so

A company's Founder, CFO, and CMO deliberate. A proposal enters the room.
Someone scores it, with real reasoning, sometimes low. The chair doesn't
override that silently. A decision comes out the other side with its
dissent still attached, not smoothed away. Someone watches this happen.

That is the Boardroom MVP. Not the repository state that permits it —
the event itself, already true the moment `deliberation_kernel` and a real
agent are in the same room together. It does not wait on every open item
in `09` to close. It waits on nothing this declaration doesn't name.

## What this changes, concretely

Every Task from here forward answers one question first, before its own
scope: **does this bring the moment closer, or does it improve something
the moment does not yet depend on?** Both kinds of work are real. Only
the first kind is urgent by declaration rather than by argument. A Task
that closes a real gap but doesn't move the moment closer waits. A Task
that moves the moment closer, even imperfectly, goes first.

This is not a priority list. Priority lists rank correct things against
other correct things. A declaration doesn't rank — it pulls. Everything
answering to this declaration is pulled toward one thing: the session
happening, witnessed, today, not eventually.

## The one path that matters right now

**Corrected this revision: the path changed, honestly, not silently.**
When this section was first written, `deliberation_kernel` lived in
`boardroom-orchestration` and the shortest path ran entirely there,
avoiding `agent-operating-system`. The Leader has since moved
`deliberation_kernel` and `aos-spec` into `agent-operating-system`. The
mechanism's home changed; the declaration has to say so rather than leave
a claim standing that's no longer true.

**The shortest path now runs through both repositories, in sequence, not
through avoiding either.** `boardroom-orchestration` is where a session
actually executes — the Foundry runtime, the turn pipeline, identity
verification (`boardroom-spec 02`). `agent-operating-system` is where the
mechanism itself now lives. The path: `boardroom-orchestration` calls into
`deliberation_kernel` as a dependency of `agent-operating-system`, wires
real Founder/CFO/CMO agents to it, runs a real proposal, produces a real
close, witnessed. Neither repository is the whole path alone anymore, and
neither's Task should be read as blocking on the other completing first —
`0001-receive-deliberation-kernel` (confirming the mechanism composes with
a real agent, in `agent-operating-system`) and `0005-first-live-session`
(running the actual session, in `boardroom-orchestration`) are two views
of the same moment, not sequential gates.

Everything about old-code merging, the full-Boardroom composition — all
real, all still true, none of it blocking this. The declaration exposed
that the fastest route to the lived MVP was hiding in plain sight before;
what it exposes now is that the route crosses a repository boundary
cleanly, because the boundary was always about where code lives, never
about where the moment gets to happen.
